ZenPlus Inventory

Changes

What was installed, removed, upgraded or swapped, on which machine and when. This article explains what is recorded, when the history starts, how upgrades are shown, what a capped list means and what the change budget does.

Applies to ZenPlus 1.24.0+ Updated 2026-10-09 Audience Operators and auditors Reading time ~9 min

01 What is recorded #

Changes are recorded inside the database at the moment a value changes, no matter which part of ZenPlus wrote it (the agent upload, the SNMP poller or the API). Four categories exist:

CategoryOnRecorded when
SoftwareServersA title appears in a server’s list (installed), disappears (removed), or its version changes (upgraded, downgraded or changed)
OSServersThe normalised operating-system version changes
FirmwareNetwork devicesThe normalised firmware version changes
HardwareNetwork devicesThe model or the serial number changes, which is the signature of a chassis swap or an RMA

What is deliberately not a change

  • The first report of a server. It becomes the baseline; nothing is an “install” on day one.
  • A value appearing for the first time (a device whose model was blank and is now known). That is discovery, not change.
  • A value going missing. A collector that momentarily reports nothing is a gap, not an upgrade, so the version is never recorded as changing to “nothing” and back.
  • An update to the normalisation rules. If a ZenPlus release reads 10.0.20348.2700 differently, no history is written for any machine.
  • Deleting a server. Its software is not logged as removed; its earlier history is kept.

The rule behind all of these is the same: a false entry in an audit trail is worse than a missing one, because history cannot be corrected afterwards.

02 The Changes page #

Time window
24 h, 7 d (the default), 30 d or 90 d. The window is stored in the address as a since time, so the exact view can be shared. A custom range from a link shows as Custom.
Statistics strip
Eight chips with the numbers in the window: All changes, Installed, Removed, Upgraded, Downgraded, OS changes, Firmware changes and Hardware changes. Click a chip to show only those changes; All changes shows everything again. Each number equals the total of the list it opens.
Changes per day
A stacked chart by category with a View as table toggle. A day with no change is still a day. Click a day to list it.
Search and filters
Search asset, product or version; switch between All assets, Servers and Network devices; narrow to one asset or one product from the links in a row. Active filters appear as chips that you can remove. The days follow your browser’s time zone.
The list
Grouped by day, newest first, one sentence per change: Google Chrome upgraded 151.0.7922.110 → 152.0.8001.12, Windows Server changed 10.0.20348.2402 → 10.0.20348.2700 (OS), FortiOS changed 7.2.5 → 7.2.8 (firmware), Serial number changed FCW2312L002 → FCW2399X777 (hardware), TeamViewer installed 15.5.3. A small label at the end of the row names the category. The machine’s name opens its flyout on the Assets page.

An upgrade or downgrade is called that only when ZenPlus can order the two versions with the product’s own version rules. Otherwise the row says changed; it never guesses.

03 When history starts #

History starts when the ZenPlus release that introduced Inventory was installed on your appliance, because that is when change capture began. Anything installed, removed or upgraded earlier was never recorded, cannot be reconstructed, and ZenPlus does not guess it from other data.

The footnote at the foot of the Changes page names that day: History starts Wed 7 Oct 2026, when change capture began. Changes older than 400 days are removed. Hover over it for the exact time and time zone. The date is the day capture began, not the day of the earliest change in the list: on a quiet estate the first recorded change may come days later, and the days between are covered by the recording, not gaps. Once the retention period has passed that day the footnote says so: Change capture began … The history you can see therefore starts …. Until the page has the date it says History starts when change capture was enabled without a day.

For auditors

The footnote exists so a gap before the start date is never mistaken for a quiet period. Quote the capture start date together with any change report you hand over (not the date of the first change in the list), and export the list for the period with CSV export.

04 Upgrades shown as one row #

Some products carry their version in their name (Java 8 Update 391, the Visual C++ redistributables). Upgrading one makes the old title disappear and a new title appear, so the server’s list shows a removal and an installation written together. Inventory pairs them: same server, same product, same moment, one added and one removed. The list shows the pair as one upgrade (or downgrade, when the versions can be ordered), for example Java 8 Update 401 upgraded 8.0.351 → 8.0.401 (replaces Java 8 Update 351) on dc1-dc-01, with a small note 1 change, 2 events. Elsewhere, such as the Overview’s recent changes and a machine’s flyout, each half is listed on its own and says (part of an upgrade).

  • The count above the list says it plainly: 56 events, 50 rows on this page (6 pairs of installation and removal shown as one upgrade). Events and rows are different numbers on purpose.
  • Below the statistics strip, a line such as Plus 3 upgrades and 1 downgrade recorded as an installation and a removal. The list shows each pair as one row. tells you how many such pairs the window holds. The Upgraded and Downgraded chips count only versions changed in place, so they equal the lists they open.
  • If a pair is split across two pages, each half says The other half of this change is on another page.

05 Capped lists #

The Windows agent sends at most 1,000 installed titles per server. It sorts the list by name and cuts the end off. A server with more installed programs than that has a capped list: the titles at the end of the alphabet are missing from every report, whether or not they are installed.

That makes changes near the cut unreliable, so ZenPlus does two things:

  • It does not treat a title that falls off the end of a capped list as removed. Only titles that sort before the last title the agent sent, and are absent, are provably uninstalled.
  • Every change recorded while a server’s list is capped carries a note in the Changes list: The list was capped at 1,000 titles when this was recorded, so this title may have been cut off rather than removed (or, for other changes, so the picture may be incomplete).

The server is also flagged Software list truncated in the Inventory health panel and in its flyout. The fix is on the agent side; the 1,000-title cap is part of the agent. See health and freshness.

06 The change budget #

A mass reinstall, a deployment that rewrites every package, or a misbehaving agent could write thousands of events for one server and drown the history. Each server therefore has a budget of about 2,000 software changes per rolling 24 hours.

  • Within the budget everything is recorded as usual.
  • The budget is checked once per report, when the report arrives. A report that starts below 2,000 is recorded whole, so one very large report can take a server past 2,000 (a server at 1,999 that reports 1,000 changes ends the day with about 3,000). That is why the limit is “about” 2,000.
  • Once a server is at or over the budget, the software part of further reports is applied to the server’s current software list but not written to history. The inventory stays correct; only the history is bounded.
  • One marker row is written for the day so the gap is visible. In the Changes list it is a dashed row that starts Change budget exceeded, then for <server>: further changes of that report were not recorded, with the note This marks a gap in the history. It is not a change of the asset. and a Gap badge at its right end. (Elsewhere the marker is an italic line without a category.)

Operating-system, firmware and hardware changes are not subject to the budget. A server that hits the budget regularly is worth investigating: something on it is rewriting its program list.

07 Deleted assets and retention #

  • Deleted assets. History outlives the machine. The row keeps the name the machine had at the time, shown as plain text with the tooltip This asset has been deleted; its history is kept. A user whose role is limited to tags does not see the changes of deleted assets, because their tags are gone with them. The footnote says so.
  • Retention. Changes are kept for 400 days by default, enough for a twelve-month audit window plus margin. An administrator can set it from 30 to 3,650 days in Inventory settings. Older events are removed once a day, and once that has started the history footnote names the earliest day still kept. Lengthening the retention does not bring back events that are already gone.
