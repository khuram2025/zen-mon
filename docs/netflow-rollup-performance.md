# Flow-history reconciliation performance

`netflow_rollup.coordinated_sweep` takes a session advisory lock dedicated to census and scheduling. It uses a connection in AUTOCOMMIT mode, so it does not hold a database transaction open while scanning history. `pg_advisory_unlock` runs on the same connection; a failed unlock invalidates the physical connection before pool return. Per-hour repair transactions retain their separate advisory lock and fresh raw-data checks.

The `netflow_rollup_census:<database>` internal system setting contains the next-due time and reusable raw-partition censuses. Successful passes publish both together. A competing worker retries in 60 seconds, then reads the shared schedule instead of repeating a completed pass. A failed pass publishes neither new cache state nor a new completion time. A completion from before a worker started cannot defer its startup reconciliation check, so restored or migrated history is checked promptly. The cache may still be reused after fresh fingerprint checks. The normal six-hour interval and earlier mutation/settling retries remain in effect. The setting requires no telemetry schema migration.

`netflow_census.RawCensusCache` fingerprints each active partition using the table UUID/schema and sorted part identities, row counts, data versions, and checksums. It computes flow-hour and received-hour totals per physical partition. Received hours can span timestamp partitions: counts and bytes are summed, and timestamp bounds are merged with minimum/maximum. Integer sums preserve UInt64 overflow semantics. The oldest-record boundary and unmasked sampling-row checks are computed from this same exact census.

Metadata is checked again after measurement. Changed or newly created partitions are reread once; continuously changing partitions are used only for the current pass and are not persisted as reusable results. Deleted partitions are discarded. Raw records remain authoritative when a repair is executed. A cache miss or rejected cache payload runs the census again.

Cold or changed partitions are read in batches of at most 16. Persisted cache state is capped at 2 MiB. An appliance with more retained partitions can evict cache entries without losing data or skipping repairs; its next pass rereads those partitions. A schema change or future change to census semantics must invalidate the cache by changing its format version.

Tests use separate scratch ClickHouse and PostgreSQL instances. `NETFLOW_TEST_PG_URL` explicitly enables PostgreSQL integration checks; never point it at an installed appliance database. Performance claims must distinguish a warm unchanged pass, a changed-partition refresh, and a cold full measurement. The cache reduces repeated work and duplicate-worker scans; it does not eliminate the initial measurement or certify unrelated query workloads.
