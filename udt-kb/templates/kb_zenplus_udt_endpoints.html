Finding endpoints: search, detail and history

The everyday task — someone gives you a MAC, an IP or a hostname and you need the switch, the port and the VLAN. Plus how to read the history when the answer is “where was it”.

Applies to ZenPlus 1.14.3+ Updated 2026-08-16 Audience Network operators + service desk Reading time ~9 min

01 Searching #

One search box, on Monitoring → User Devices → Endpoints, accepts whatever identifier you happen to have.

MAC address
Any format. aa:bb:cc:dd:ee:ff, aa-bb-cc-dd-ee-ff, aabb.ccdd.eeff and aabbccddeeff are all normalised to the same address, so you can paste straight from a Cisco CLI, a Windows ipconfig or a DHCP lease.
IP address
Matches the current IP and historical bindings. An IP that has since been reassigned still finds the device that used to hold it.
Hostname
Partial match. Hostnames come from reverse DNS or from a correlated Active Directory logon, so they are only present where one of those resolved.
Vendor
Partial match on the NIC manufacturer derived from the MAC prefix — canon, hikvision, vmware.
Username
Partial match, once Active Directory correlation is configured.
Searching a partial MAC

A fragment that is not a complete MAC falls back to a text match, so typing an OUI like 00:50:56 returns every VMware endpoint. A complete MAC is matched exactly, which is much faster on a large estate.

02 Filters and counters #

The six tiles across the top are both a summary and a filter — click one to scope the list to it.

TileCounts
EndpointsEvery endpoint ever seen, excluding ignored ones
Active nowSeen in the last 15 minutes
RogueMatched no allow rule. Stays at zero until an allow list exists
WatchedOn the watch list, by rule or pinned by an operator
New (24h)First seen anywhere on the network in the last 24 hours
Logins (24h)Active Directory logon events correlated in the last 24 hours

Alongside them: quick filters for Active, Rogue, Watched, New and Random MAC, and a row of type chips with live counts. The type chips are generated from whatever types and custom groups actually exist, so any group you create in Classification appears here as a filter automatically.

Every column header re-sorts — last seen, first seen, MAC, IP, hostname, vendor or type — and the list pages 50 at a time.

03 Reading the columns #

Endpoint
The device type icon and label, or the hostname when one is known. The dot to its left is the live indicator.
MAC
The endpoint's identity. This is the primary key — everything else about an endpoint can change, including its IP and its port.
IP address
The most recent binding learned from an ARP or neighbour table. A dash means no layer-3 device has reported this MAC.
Vendor
Derived from the MAC's OUI prefix against the IEEE registry.
Connected to
Switch and port. An indirect badge means the device has only been seen on an uplink — the port shown is a transit path, not where it is plugged in. A dash means no switch has reported it at all.
VLAN
The VLAN the MAC was learned in, where the switch reports a VLAN-aware table.
User
The last correlated Active Directory user.
Last seen
Time since the endpoint last appeared in any table.

The chip at the end of each row carries the authorisation state: Unclassified until an allow list exists, then Authorised or Rogue. Random MAC appears instead for privacy addresses.

04 Endpoint detail #

Clicking any endpoint opens its full record. The summary strip answers the immediate question — Current location, VLAN, Last user, Connected for, First seen and Last seen — and the panels below give the history.

Three actions sit in the header, all requiring the operator role:

Watch
Pins this endpoint to the watch list. Every time it reappears on the network an event is raised, which an alert rule can act on.
Flag rogue
Marks it unauthorised, and pins that decision — the rule engine will not overwrite a manual verdict on later sweeps.
Ignore
Hides it from every UDT view and excludes it from flagging. Use it for the appliance's own interfaces, test gear and anything else that is noise.

The Type dropdown re-classifies the endpoint by hand. A manual type outranks both classification rules and the automatic heuristics; setting it back to Auto returns the endpoint to rule-and-heuristic control immediately.

05 Connection history #

Each entry is a session: a continuous period during which the endpoint was seen on one port, with a start, an end and a duration. The newest sits at the top; an open session shows → now and a connected badge.

By default only direct sessions are listed — the access ports where the device was genuinely plugged in. Uplink sightings are collapsed behind Show N uplink sightings, because a single device commonly appears on dozens of trunk ports and listing them inline would bury the answer. See direct versus indirect.

Why one device has many short sessions on the same port

A session closes when the endpoint has been unseen for 15 minutes and opens again when it comes back. A laptop that sleeps, a phone that goes idle, or a device whose MAC ages out of the forwarding table between polls will therefore show a run of sessions on the same port rather than one long one. The pattern is normal; the port is what matters.

IP address history alongside it lists every address the endpoint has held, with the source (ARP for IPv4, ND for IPv6 neighbour discovery) and whether the binding is still current. A binding goes past after 24 hours without being seen. This is the panel that answers “which device had 10.20.4.31 last Tuesday”.

06 Randomised MAC addresses #

Modern phones and laptops rotate a private MAC per network by default. UDT detects these by the locally administered bit in the first octet and tags them Random MAC.

Two consequences worth knowing:

  • No vendor. A randomised address has no real OUI, so the vendor column is empty and vendor-based classification cannot work on it.
  • No continuity. The same physical device becomes a new endpoint each time it rotates, inflating the “new endpoint” count and making per-device history shorter than reality.

If randomised addresses are noise for you, filter them out with the Random MAC chip, or add an ignore rule. If they matter for compliance, the durable fix is on the network side — require registered MACs, or disable private addressing through device management policy.

08 A worked example #

The service desk reports that a workstation at 172.20.30.40 keeps dropping off the network, and the user says “it was fine last week”.

Search the IP

One result. The endpoint is a workstation, NIC vendor Wistron, currently on ACC-SW-07 port 4/1/20, VLAN 230, connected for 1 day 6 hours.

Check whether it really is dropping

Connection history shows one long current session preceded by a run of 15-minute to 3-hour sessions on the same port. The port is stable; the device is going quiet — sleep or power management, not a cabling fault.

Check whether the IP changed

IP history shows 172.20.30.40 active now and 172.20.98.234 as past, last seen six days ago. So it did move subnets last week, which explains “it was fine then” if anything was pinned to the old address.

Confirm who uses it

With Active Directory connected, the user logins panel names the account, and you have a person to call rather than a MAC address.
