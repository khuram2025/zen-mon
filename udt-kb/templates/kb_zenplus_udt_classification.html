ZenPlus UDT

Device classification and vendor groups

Turning 1,700 MAC addresses into an inventory you can reason about — how the automatic classifier works, why it says “Unknown”, and how one rule per vendor fixes it.

Applies to ZenPlus 1.14.3+ Updated 2026-08-16 Audience Network operators Reading time ~8 min

01 Why classification matters #

An endpoint's type is not cosmetic. It is a filter on every UDT screen, it shapes the vendor and capacity reporting, and it is how you separate the 400 workstations you expect from the four things you do not. A network where everything is “Unknown” is a list; a network where everything is typed is an inventory.

UDT ships with ten built-in types — workstation, server, phone, printer, access point, camera, virtual, network, IoT and unknown — and lets you add as many groups of your own as you like.

02 How the classifier decides #

Every 60 seconds the UDT sweeper re-types any endpoint still sitting at Unknown under automatic control. It has three signals, checked in this order:

Is the endpoint a device ZenPlus already monitors?

If the MAC belongs to a device in your inventory, its type comes straight from there — a monitored switch becomes network, a monitored server becomes server. This is the strongest signal because it is not a guess.

Does the hostname say what it is?

Naming conventions are matched next: SEP<mac> and anything containing phone; prn-, -prt and printer; cam-, camera, ipcam; ap- and accesspoint; srv-, esxi, nas- and server.

What does the NIC vendor suggest?

Finally the OUI vendor is matched against a built-in list — Polycom and Yealink are phones, Hikvision and Axis are cameras, Ubiquiti and Aruba are access points, VMware and Proxmox are virtual, Canon and Lexmark are printers, and so on.

Vendor is a hint, not a fact

The OUI identifies who made the network chip, not the product. Intel makes the NIC in most corporate laptops but also in servers and appliances; Wistron and Compal build laptops for several brands. The vendor heuristic is deliberately conservative — when it is not confident, it leaves the endpoint Unknown rather than guessing wrong, which is what classification rules are for.

03 Precedence #

Three sources can set a type. They rank strictly, and the rank is visible on the endpoint as its type source:

RankSourceSet byCan be overwritten by the sweeper?
1 — highestmanualAn operator choosing a type on the endpoint pageNever
2ruleA classification rule; lowest priority number winsOnly by another rule, or when no rule matches any more
3 — lowestautoThe built-in heuristics aboveFreely, on every sweep

The practical consequence: rules are safe to experiment with. Editing or deleting a rule re-evaluates every endpoint immediately and tells you how many changed, and anything a human pinned by hand is untouched. An endpoint that stops matching any rule falls back to automatic control rather than being stranded on a stale type.

To un-pin a manual decision, set the type back to Auto on the endpoint page — the rules and heuristics re-run on that endpoint straight away.

04 The vendor rollup #

The lower half of the tab lists every NIC vendor on your network with its endpoint count and how those endpoints are currently typed. It is the fastest way to find classification work worth doing: scan the Current groups column for large blocks sitting in Unknown.

A vendor with 144 endpoints all marked Unknown is one rule away from being 144 correctly-typed devices. The Rule button on the row opens the rule dialog pre-filled with that vendor, so you only have to choose the group.

05 Writing a classification rule #

A rule is a match condition plus the group to assign. Seven match types are available, and they are the same set used by watch, allow and ignore rules:

Match onPatternTypical use
MAC address00:1a:2b:3c:4d:5e, any separatorOne specific device
MAC / OUI prefix70:c9:c6 or 70c9c6Everything from one manufacturer — the workhorse
Vendorhikvision, substring matchVendors with many OUI blocks
Hostnameprn-*, *-cam??Naming conventions; * and ? are wildcards
IP address10.20.4.31A pinned device
IP range10.20.4.1 - 10.20.4.254A DHCP scope reserved for one device class
Subnet10.20.4.0/24A whole VLAN of one kind of device

Priority resolves overlap: the lowest number that matches wins. Leave the default of 100 for broad vendor rules, and use a lower number such as 10 for narrow exceptions that must beat them — for example a whole OUI mapped to Camera at priority 100, with one subnet of the same vendor's encoders mapped to Server at priority 10.

The Matches column on the rules table shows how many endpoints each rule currently catches, which is the quickest way to spot a rule whose pattern never fires.

Rules apply instantly

Creating, editing or deleting a rule re-evaluates the whole endpoint table on the spot and reports how many endpoints changed. You do not wait for the next sweep, and you can undo by deleting the rule.

06 Custom groups #

The built-in types rarely describe a real estate exactly. Type any lowercase slug into a rule's group field — door-access, ups, medical, pos-terminal, timeclock — and the group is created on use.

Custom groups behave exactly like built-in types everywhere: they get a chip with a live count on the Classification and Endpoints tabs, they filter the endpoint list, and they can be assigned by hand on an individual endpoint. A group with no endpoints and no rules simply stops appearing.

Slugs are lowercase letters, digits, hyphens and underscores, up to 30 characters, and must start with a letter or digit.

Group by who owns it, not just what it is

The most useful custom groups often follow responsibility rather than hardware — facilities, security-team, clinical. When something appears on a port that should not, knowing which team owns that class of device is worth more than knowing its model.

07 When everything is Unknown #

If every endpoint has no vendor and everything is Unknown, the problem is not the classifier — it is the OUI database. UDT resolves vendors from the IEEE registry, which the appliance downloads automatically when the table is empty, retrying every six hours.

On an appliance with no outbound internet access that download never succeeds, and without vendors the heuristics have nothing to work with. Symptoms and fixes:

SymptomCauseFix
Every vendor blank, everything UnknownOUI table empty — no internet accessAllow outbound HTTPS, or ask Zentryc support for an offline OUI bundle
Most vendors resolve, a few blankGenuinely unregistered or randomised MACsNormal — see randomised MACs
Vendors resolve, types still UnknownVendor not in the built-in heuristic listWrite a classification rule — this is the expected workflow

The third row is normal and not a defect. The built-in list covers common vendors of obviously-typed hardware; specialised equipment — access-control readers, UPS management cards, radios, medical devices — is meant to be classified by you, because only you know what it is.
