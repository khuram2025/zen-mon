ZenPlus UDT

Troubleshooting the User Device Tracker

The symptoms operators actually hit, in order of how often they hit them — each with the underlying cause and the command that proves it.

Applies to ZenPlus 1.14.3+ Updated 2026-08-16 Audience Network operators Reading time ~10 min

On this page

  1. A switch shows no endpoints
  2. An endpoint has an IP but no port
  3. Everything shows as indirect
  4. A device shows the wrong port
  5. Vendors are all Unknown
  6. Rogue count stuck at zero
  7. No user logins
  8. Too many endpoints

01 A switch shows no endpoints #

By far the most common problem, and on Cisco IOS almost always the same cause. The switch polls fine, interfaces and ARP are healthy, the Settings tab shows a recent Last poll — and Endpoints is zero.

On a Cisco IOS switch, check the vlan- context grant first

UDT may report “bridge MIB returned no MACs (check the SNMP view exposes 1.3.6.1.2.1.17)”. On Cisco IOS and IOS-XE the view is usually not the problem — the per-VLAN context grant is. Cisco refuses the per-VLAN walk silently, so the generic message appears even when the real cause is authorisation. Rule out the context grant before you touch the view.

Prove it in two commands

Run these from any Linux host with the same credential ZenPlus uses. The first should return rows; the second is the one that matters:

# 1. Default context — bridge port to ifIndex map
snmpwalk -v3 -l authPriv -u netmon -a SHA -A <AUTH> -x AES -X <PRIV> \
         <switch-ip> 1.3.6.1.2.1.17.1.4.1.2

# 2. VLAN 1 context — the forwarding table itself
snmpwalk -v3 -l authPriv -u netmon -a SHA -A <AUTH> -x AES -X <PRIV> \
         -n vlan-1 <switch-ip> 1.3.6.1.2.1.17.4.3.1.2
ResultDiagnosisFix
#2 returns authorizationError (access denied to that object)The v3 group is not authorised for vlan- contextsAdd snmp-server group GRP v3 priv context vlan- match prefix
#1 is empty tooThe read view excludes the bridge MIBInclude 1.3.6.1.2.1.17 in the view
Both time outCredential or ACL problem, not a UDT problemCheck the SNMP ACL permits the appliance
Both return rows, UDT still emptyGenuine — the switch really has no learned MACsExpected on a core or top-of-rack switch with only infrastructure ports

On SNMPv2c there is nothing to grant: ZenPlus uses community@vlan indexing, which IOS supports natively. Verify with snmpwalk -v2c -c <community>@1 <switch-ip> 1.3.6.1.2.1.17.4.3.1.2.

On non-Cisco platforms, check the VLAN-aware table directly — if this returns rows, UDT will work:

snmpwalk -v2c -c <community> <switch-ip> 1.3.6.1.2.1.17.7.1.2.2.1.2

Full configuration examples are in Setup and permissions.

02 An endpoint has an IP but no switch port #

Connected to shows a dash while the IP and vendor are populated. The endpoint was learned from a router or firewall ARP table, and no switch has reported that MAC.

  1. Is the switch monitored at all? If the device sits behind an unmanaged switch, or a switch not yet added to ZenPlus, there is nothing to learn from. Add it.
  2. Is the switch returning its bridge table? Check the Endpoints column for that switch on the Settings tab — if it is zero, go back to section 1.
  3. Is the port excluded from UDT? An excluded port keeps its capacity statistics but produces no endpoints. Check the UDT toggle on the Switch Ports tab.

This is expected and harmless for anything that is not behind a monitored switch — VPN clients, devices on a partner network, or hosts on a segment routed by a firewall you monitor but switched by hardware you do not.

03 Every endpoint shows as indirect #

Endpoints are found, but they all carry an indirect badge and no access port is ever identified. That means uplink detection has classified the access ports as uplinks.

Check the Role column on the Switch Ports tab and read the reason next to it:

Reason shownWhat went wrongFix
lldp / cdp on an access portThe neighbour advertises an identity that reads as infrastructure — docking stations and some laptops do thisOverride the port to access; the override is permanent
mac_count on a real access portEight or more MACs behind one port — a desk switch, a hypervisor, or an access pointOverride to access if you want its clients attributed there
trunkThe switch genuinely reports the port as trunkingCorrect — fix the switch configuration if it should not be a trunk
Every port on the switch is uplinkNormal on a core or top-of-rack switchNothing to do — that switch has no access ports

Overrides take effect on the next poll and re-shape the endpoint list for everything behind that port. See overriding the verdict.

04 A device shows the wrong or an old port #

Almost always timing rather than error. Three delays stack up:

Switch MAC ageing
The switch keeps a learned MAC for its ageing time — commonly 300 seconds — after the device stops sending. UDT cannot see a move the switch has not noticed.
Poll interval
UDT polls every 300 seconds by default. A move can be up to one interval old before it is read.
Session grace
A session is only closed after 15 minutes without a sighting, so the old port lingers briefly. This is deliberate — it stops one missed poll from tearing down every live session.

Worst case is therefore roughly 15–20 minutes for a move to fully settle. If you need tighter resolution, lower the poll interval on the UDT Settings tab — globally or on the switches that matter. The cost is more SNMP load on those switches.

If a port is wrong by hours, that is not timing. Check that the switch is still polling successfully at all.

05 Vendors are all Unknown #

If every endpoint has a blank vendor, the OUI table is empty. ZenPlus downloads the IEEE registry automatically when it finds the table empty and retries every six hours, falling back to a secondary source if the primary is unreachable.

On an air-gapped or restricted appliance that download never completes. Either permit outbound HTTPS from the appliance, or ask Zentryc support for an offline OUI bundle. Once seeded, new endpoints resolve their vendor as they are discovered and existing endpoints are backfilled.

If most vendors resolve and a few do not, that is normal: randomised privacy MACs have no real OUI. See randomised MAC addresses.

06 The rogue count is stuck at zero #

This is configuration, not a fault. Rogue detection does nothing until an allow list exists — with no allow rules, every endpoint is unclassified, which is neither authorised nor rogue, and the tile reads zero.

Create allow rules on the Watch Lists tab. Read rolling it out safely first — enabling detection on a mature network in one step will produce a large first batch of findings.

07 No user logins appear #

Start on the Settings tab: the domain controller row carries the last poll, its status and the last error. Use the poll action to run it immediately rather than waiting for the next interval — the error it returns is the diagnosis.

The full matrix is in User logins. The three that catch people out:

  • Authentication succeeds but access to the log is denied — the account is in Remote Management Users but not Event Log Readers. Both are needed.
  • Status OK, zero events — success auditing is not enabled for the Logon and Kerberos subcategories. Check with auditpol /get.
  • Events recorded but nothing links to an endpoint — UDT has no IP data for the subnets those workstations live on. Add the router or firewall that serves them.

Test WinRM reachability from the appliance shell. WinRM rejects a plain GET, so 405 is success:

curl -sk -o /dev/null -w '%{http_code}\n' http://dc01.corp.local:5985/wsman

08 Far more endpoints than you have devices #

UDT counts every MAC address it has ever seen, which is legitimately larger than your device count. The usual contributors, in order of size:

SourceWhyWhat to do
Randomised MACsPhones and laptops rotate a private address per network, creating a new endpoint each timeFilter with the Random MAC chip, or add an ignore rule
Virtual machinesEvery VM NIC is a real MAC on the wireExpected — they classify as virtual
Guest and BYOD wirelessEvery visitor device is trackedIgnore the guest subnet if it is out of scope
Lab and test networksConstant churnIgnore the subnet, or exclude the ports
Historical devicesEndpoint identities are never prunedUse the Active filter for what is on the network now

The number to trust for “what is on my network right now” is Active now, not the total. The total is an historical inventory.

Still stuck?

Collect the switch hostname, the output of the two snmpwalk commands in section 1, and the Ports monitored / Endpoints / Last poll values from the UDT Settings tab, then contact Zentryc support. Those four facts identify nearly every collection problem without a further round trip.
