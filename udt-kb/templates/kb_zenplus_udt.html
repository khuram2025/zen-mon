User Device Tracker (UDT)

01 What UDT answers #

The ZenPlus User Device Tracker is a layer-2 endpoint tracker. It reads the forwarding tables of your switches and the ARP tables of your routers and firewalls over SNMP, then stitches those fragments into one identity per device: a MAC address, the IP addresses it has held, the switch port it is plugged into, the VLAN it lives on, the vendor that made its network card, and — if you connect a domain controller — the user who last logged in on it.

It exists to answer questions that are otherwise a manual hunt across a dozen CLI sessions:

  • Where is this device? Give it a MAC, IP or hostname and it returns the switch, the port and the VLAN — right now, or on any day in the last 90 days.
  • What is on my network that should not be? Define what is authorised; everything else is flagged as a rogue endpoint the moment it appears.
  • Who was using it? Active Directory logon events are correlated to endpoints, so a MAC becomes a person.
  • Have I run out of switch ports? Per-switch used, free and uplink counts with a daily trend, so port exhaustion is a purchase decision rather than a surprise.
  • What changed? New endpoints, endpoints that moved port, watched devices appearing and rogues detected all land in one activity feed and can raise alerts.

02 The screens, and what each one answers #

UDT lives under Monitoring → User Devices in the appliance. Seven tabs, each with a single job.

Endpoints
Where is this device? Search by MAC, IP, hostname, user or vendor and open any endpoint for its full connection and IP history.
Switch Ports
Which ports are used, free or uplinks? A per-switch port map with the endpoints on each port, plus remote shutdown and per-port UDT exclusion.
User Logins
Who used which machine? Active Directory logon events rolled up per user and linked to endpoints.
Classification
What kind of device is this? NIC-vendor rollups and override rules that put endpoints into built-in types or your own groups.
Watch Lists
What is authorised? Allow, watch and ignore rules — the allow list is what turns rogue detection on.
Activity
What changed? New endpoints, endpoint moves, watch hits, rogue detections and port actions over 24 hours, 7 days or 30 days.
Settings
Which devices does UDT poll, how often, with which credential — and which domain controllers supply user logins.

03 How the data is collected #

Understanding this pipeline explains almost every question people ask about UDT — why a switch shows no endpoints, why a device appears on six ports at once, and why a change takes a few minutes to show up.

every switch / firewall you monitor with SNMP
      │
      │  ZenPlus poller, every 300s (configurable, globally or per device)
      ▼
  ┌─ BRIDGE-MIB / Q-BRIDGE-MIB  ──▶ MAC  →  switch port  (+ VLAN)
  ├─ IP-MIB ARP + IPv6 neighbour ──▶ IP   →  MAC
  ├─ LLDP-MIB / CDP cache       ──▶ neighbours, uplink detection
  └─ VLAN inventory (Q-BRIDGE, Cisco VTP)
      │
      ▼
  correlation: one endpoint identity per MAC, sessionised per port
      │
      │  UDT sweeper, every 60s
      ▼
  classify → apply allow / watch / ignore rules → reverse-DNS →
  daily port-capacity snapshot → prune beyond 90 days
      │
      │  UDT alert evaluator, every 30s
      ▼
  udt_new_endpoint · udt_rogue_endpoint · udt_watch_endpoint
  udt_endpoint_moved · udt_port_capacity_pct   →  your alert channels

  (optional, separate) domain controller ──WinRM──▶ Security log
  events 4624 / 4768 / 4769  →  user ↔ endpoint correlation

Two SNMP sources do most of the work, and they answer different halves of the question. A switch gives you MAC → port. A router or firewall gives you IP → MAC. UDT joins them on the MAC. If you only monitor switches, you get ports without IP addresses; if you only monitor firewalls, you get IP addresses with no port. Monitor both.

Why a change takes a few minutes

A device that moves port is not seen instantly. The switch has to age its forwarding table, the poller has to run (default every 5 minutes), and a session is only closed once the endpoint has been missing for 15 minutes — roughly three missed polls, so a single dropped poll does not tear down a live session. Shorten the poll interval if you need tighter resolution.

04 Direct versus indirect #

This is the single most important concept in UDT, and the one that surprises people first.

A MAC address does not appear in the forwarding table of only one switch. It appears in the table of every switch in its path — on the access port where the device is really plugged in, and on the uplink or trunk port of every switch upstream of it. A laptop on one access port can legitimately show up on fifteen ports across your estate.

UDT resolves this by classifying every port as access or uplink, and then marking each sighting accordingly:

SightingMeansShown as
DirectSeen on a port classified as an access port — the device is physically plugged in hereThe endpoint's location; drives “Connected to”
IndirectSeen on an uplink or trunk — the traffic merely passes throughHidden behind Show N uplink sightings on the endpoint page

Uplinks are detected automatically, in this order, first match winning:

  1. An LLDP or CDP neighbour that is itself network infrastructure — another monitored device, or a neighbour whose system description looks like a switch, router, firewall or a network OS (IOS, NX-OS, JunOS, EOS, RouterOS…).
  2. Cisco VTP trunk status reporting the port as trunking.
  3. MAC count — eight or more distinct MACs learned on one port.

You can override the verdict per port on the Switch Ports tab when the heuristics get it wrong — a manual override always wins and is never recomputed. See Switch ports, uplinks and capacity.

05 Retention and scale #

DataKept forNotes
Endpoint identitiesIndefinitelyOne row per MAC ever seen; first-seen and last-seen are never pruned
Port sessions (connection history)90 daysClosed sessions only; the active session always survives
IP history90 daysA binding goes inactive after 24 hours unseen
Activity events90 daysNew endpoint, moved, rogue, watch, port actions
User logins90 daysFrom domain controllers
Port capacityIndefinitelyOne row per switch per day
An endpoint is “active” if it was seen in the last 15 minutes

Everywhere in UDT — the Active now counter, the green dot on a row, the Active filter — “active” means last seen within 15 minutes. It does not mean the device is powered on; it means a switch still had it in a forwarding table at the last poll.

06 Where to start #

Give UDT what it needs from the network

An SNMP credential that can read the bridge tables on your switches — on Cisco IOS that requires one extra command most read-only configurations are missing. See Setup and permissions.

Confirm endpoints are landing

Settings shows ports monitored, endpoints and last poll per device. A switch with a last poll but zero endpoints is the classic symptom — troubleshoot it here.

Tidy up classification

Turn the biggest blocks of “Unknown” into meaningful groups with one rule per vendor. See Classification.

Decide what is authorised

Until an allow rule exists, nothing is ever flagged rogue. See Watch, allow and ignore lists.

Connect Active Directory

Turns MAC addresses into people. See User logins.
