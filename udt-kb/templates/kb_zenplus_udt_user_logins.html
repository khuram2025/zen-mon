ZenPlus UDT

User-to-device correlation with Active Directory

Turning a MAC address into a person. Agentless, read-only, and driven entirely by logon events the domain controllers are already writing.

Applies to ZenPlus 1.14.3+ Updated 2026-08-16 Audience Windows + network admins Reading time ~8 min

01 How it works #

Nothing is installed on any Windows machine. On a schedule — 300 seconds by default — ZenPlus opens a WinRM session to each configured domain controller, runs a single read-only PowerShell query against the Security event log, and closes the session.

ZenPlus appliance
      │  WinRM (TCP 5985 / 5986), NTLM by default
      ▼
domain controller — Security event log
      │  Get-WinEvent, events 4624 / 4768 / 4769, newest 500
      ▼
  user + workstation IP + workstation name
      │  match on active IP binding, then hostname
      ▼
  UDT endpoint  ──▶  "Last user" on the endpoint, and the User Logins tab

Each poll asks only for events newer than the last one already recorded, so a controller is never re-read from the beginning. The very first poll looks back 30 minutes to seed the timeline.

Event IDWhat it recordsWhy UDT reads it
4624An account was successfully logged onCovers NTLM and any environment where Kerberos is not the whole story
4768A Kerberos TGT was requestedThe workstation's IP at domain sign-in
4769A Kerberos service ticket was requestedKeeps the user-to-IP association fresh through the working day
Broader than the SolarWinds equivalent

SolarWinds UDT reads only the Kerberos events, 4768 and 4769. ZenPlus also consumes 4624, so NTLM-only and mixed environments still attribute users to endpoints instead of showing an empty tab.

02 What Windows needs to allow #

One ordinary domain account, with no administrative rights, needs exactly two grants on each domain controller. Full commands, audit-policy checks and connectivity tests are in Setup and permissions; in short:

  • Event Log Readers A built-in domain-local group that grants read access to the Security log. Add the service account with Add-ADGroupMember.
  • Remote Management Users Allows a WinRM session without making the account an administrator.
  • WinRM listening, and reachable TCP 5985 (HTTP, message-level encrypted) or 5986 (HTTPS) from the appliance.
  • Success auditing enabled For Logon, Kerberos Authentication Service and Kerberos Service Ticket Operations. Kerberos auditing is on by default on domain controllers; Logon sometimes is not.
What the account can and cannot do

The account can read the Security event log and open a PowerShell session. It cannot change configuration, read other logs, or access file shares by virtue of these grants. The credential is stored encrypted on the appliance and is only ever used against the domain controllers you configure.

03 How a logon becomes an endpoint #

A logon event carries a username, a workstation IP address and sometimes a workstation name. UDT matches it to an endpoint in two passes:

By IP address

The event's client IP is matched against endpoints' current IPs and their active historical bindings. This is the reliable path, because it uses the same ARP data that produced the endpoint in the first place.

By workstation name

If no IP matched — the event had none, or the address is not one UDT knows — the workstation name is matched against endpoint hostnames, case-insensitively.

Recorded either way

A logon that matches no endpoint is still stored and still appears under User Logins. It just has no device to link to, which is itself a useful signal: the machine is on a segment UDT cannot see.

When a match is found, the endpoint's Last user is updated — but only if the event is newer than the one already recorded, so a batch of out-of-order events cannot make an old logon look current. A user login entry is added to the endpoint's activity.

Machine accounts (names ending in $) and the ANONYMOUS LOGON, SYSTEM, LOCAL SERVICE and NETWORK SERVICE principals are filtered out on the domain controller itself, before anything is sent back — so the feed is real users only and the volume stays manageable.

04 Reading the User Logins tab #

The left pane rolls up every user seen, with their domain, total logon count, how many distinct endpoints they have used and when they last signed in. Selecting a user shows their recent logons — event type, logon type, IP, workstation and time — and the endpoints associated with them.

The same data appears from the other direction on any endpoint's detail page, under User logins, which is usually where you meet it: you started from a port or an IP, and you want the person.

Once correlation is running, the user match type becomes available in watch, allow and ignore rules and in classification rules — so you can, for example, watch every endpoint a set of service accounts signs into.

05 What it can and cannot tell you #

This is authentication data, not session data, and the distinction matters when someone asks it to answer a security question.

It can tell youIt cannot tell you
Which account most recently authenticated from this device's IPWho is physically sitting at the device now
Which devices an account has signed in fromWhether the user is still logged on — logoffs are not tracked
When a logon happened, to the secondAnything about local (non-domain) accounts
That a machine authenticated from an unexpected subnetActivity on devices that never authenticate to the domain

Shared workstations attribute to whoever most recently authenticated. Terminal servers and VDI hosts, where many users authenticate from one IP, will show a rapidly changing last user on a single endpoint — correct, but rarely useful. Consider ignoring those endpoints or reading them only through the per-user view.

06 When no logins appear #

The controller row on the Settings tab shows the last poll, its status and the last error. Work down this list:

Status / errorCauseFix
No status at allNever polledUse the poll action on the row to run it now and surface the real error
Connection timed outWinRM unreachableCheck TCP 5985/5986 and that the WinRM service is running
Authentication failureWrong credential, or the account is not in Remote Management UsersVerify the domain prefix on the credential and the group membership
Access denied on the logNot in Event Log ReadersAdd-ADGroupMember -Identity 'Event Log Readers'
Status OK, zero eventsAuditing disabled, or genuinely no logons in the windowCheck auditpol for the three subcategories
Events recorded, no endpoints linkedCorrelation found nothing to matchAdd the router or firewall for those subnets so UDT learns the IPs
pywinrm not installedNon-standard appliance buildContact Zentryc support — it ships by default

The last row but one is the most common non-obvious case. Correlation is only as good as UDT's IP knowledge: if no layer-3 device reports ARP for the subnet a workstation lives on, its logons arrive with an IP that matches no endpoint. Adding that router or firewall to ZenPlus fixes the whole subnet at once — see firewalls and routers.
