ZenPlus UDT

Setup and permissions: switches, firewalls and Active Directory

Exactly which SNMP objects UDT reads, the one Cisco command that read-only configurations almost always miss, and the Windows rights a domain controller needs for agentless user correlation.

01 What you need #

UDT is agentless in both directions. Nothing is installed on switches, and nothing is installed on Windows hosts or domain controllers. Everything is read over SNMP and WinRM.

  • SNMP read access to your switches v2c community or v3 user, able to read the bridge forwarding tables. Read-only is enough for everything except remote port shutdown.
  • SNMP read access to a router or firewall This is what supplies IP addresses. Without it you get switch ports with no IPs.
  • UDP 161 from the appliance to each device Plus the device's SNMP ACL permitting the appliance's IP.
  • Optional — a domain service account For user correlation: read access to the Security event log and WinRM access on each domain controller. TCP 5985 or 5986 from the appliance.
Least privilege

Everything UDT does by itself is read-only. Write access is needed only if you want to shut down or re-enable a switch port from the ZenPlus UI, which is an explicitly separate, audited action — see remote port control. Give the monitoring account a read-only community or a v3 user with a read view and no write view.

03 Cisco: the per-VLAN requirement #

This is the number one reason a Cisco switch shows zero endpoints

Cisco IOS and IOS-XE do not publish the MAC forwarding table in the default SNMP context. Each VLAN has its own instance. A perfectly good read-only credential that returns interfaces, CPU and ARP will return nothing at all from the bridge tables until per-VLAN access is granted.

SNMPv2c — community string indexing

With v1/v2c, IOS supports community indexing natively: querying with <community>@<vlan> returns that VLAN's bridge table. ZenPlus does this automatically — it enumerates VLANs from VTP, then walks the bridge table once per VLAN using the suffixed community. No extra switch configuration is required, beyond a working read-only community:

snmp-server community ZpReadOnly RO 20
!
ip access-list standard 20
 permit 10.12.50.81

SNMPv3 — the context vlan- grant

SNMPv3 has no community string, so the per-VLAN instances are reached through named contexts: vlan-1, vlan-20, vlan-221 and so on. The group must be authorised for that context prefix. Without the second snmp-server group line below, every per-VLAN walk is refused with authorizationError and UDT sees no MAC addresses:

! Read view — the standard MIBs plus the Cisco enterprise tree
snmp-server view ZP_VIEW iso included
!
! The group, granted BOTH the default context and every vlan-* context
snmp-server group ZP_GRP v3 priv read ZP_VIEW
snmp-server group ZP_GRP v3 priv context vlan- match prefix read ZP_VIEW
!
! The user
snmp-server user netmon ZP_GRP v3 auth sha <AUTH_PASSWORD> priv aes 128 <PRIV_PASSWORD>

Verify it from any Linux host that can reach the switch. The first walk should return rows; the second is the one that matters:

# Default context — bridge port to ifIndex map (should return rows)
snmpwalk -v3 -l authPriv -u netmon -a SHA -A <AUTH> -x AES -X <PRIV> \
         10.10.10.221 1.3.6.1.2.1.17.1.4.1.2

# VLAN 1 context — the forwarding table itself
snmpwalk -v3 -l authPriv -u netmon -a SHA -A <AUTH> -x AES -X <PRIV> \
         -n vlan-1 10.10.10.221 1.3.6.1.2.1.17.4.3.1.2

If the second command answers authorizationError (access denied to that object), the context vlan- match prefix line is missing or the view does not include 1.3.6.1.2.1.17.

Nexus and Meraki behave differently

Cisco NX-OS publishes the forwarding table in the default context and needs none of this — a plain read-only v3 user is enough. Cloud-managed Meraki switches do not expose per-port bridge tables over SNMP at all and cannot be tracked by UDT.

04 Other switch vendors #

Most non-Cisco switches implement the VLAN-aware Q-BRIDGE table in the default context, which means a single ordinary read-only credential is all UDT needs. The rule of thumb: if a plain snmpwalk of 1.3.6.1.2.1.17.7.1.2.2.1.2 returns rows, UDT will work.

Aruba / HPE (ArubaOS-CX, ArubaOS-Switch)Q-BRIDGE in the default contextA standard SNMPv3 user with a read view covering iso. Nothing special.
Cisco NX-OSQ-BRIDGE in the default contextStandard read-only v3 user or v2c community.
Juniper EX / QFXBoth bridge tables in the default contextStandard read-only v3 user; ensure the view includes .1.3.6.1.2.1.17.
Extreme (EXOS)Q-BRIDGE in the default contextStandard read-only credential.
FortiSwitch (managed)Via the managing FortiGatePoll the FortiGate for ARP; managed-switch port data depends on firmware.

Check before you file a bug

Vendor behaviour varies by firmware release far more than by vendor. Before assuming ZenPlus is at fault, run the snmpwalk above against the switch with the same credential ZenPlus uses. If the walk is empty from the command line, it is empty for UDT too, and the fix is on the switch.

05 Firewalls and routers — where IP addresses come from #

Switches know MAC addresses and ports. They rarely know IP addresses. The IP half of every endpoint comes from the ARP and IPv6 neighbour tables of the layer-3 devices that route those VLANs — typically a firewall pair or a core switch doing inter-VLAN routing.

Nothing special is needed: add the device to ZenPlus with SNMP read access and leave UDT enabled for it. It contributes no ports and no endpoints of its own, but it fills in the IP addresses for everything the switches found. A single busy firewall commonly supplies more than a thousand IP-to-MAC bindings per poll.

Endpoints with an IP but no port

An endpoint showing an IP address and a dash under Connected to was learned from an ARP table but has not been found in any switch forwarding table. Either it sits behind a switch you are not monitoring, or that switch is not returning its bridge table — which is nearly always the Cisco per-VLAN problem.

06 Adding devices to UDT #

UDT has no device inventory of its own. It reuses the devices ZenPlus already monitors, and it is on by default for every SNMP-enabled device — so in most deployments there is nothing to add.

Create the SNMP credential

Go to Administration → Credentials → SNMP and add the community or v3 user. One credential is normally shared by a whole switch estate.

Add the devices

Monitoring → Devices to add them by IP, or use Discovery to sweep a subnet and import what answers SNMP. Assign the credential during import.

Confirm UDT is enabled for them

Monitoring → User Devices → Settings lists every SNMP device with a UDT toggle. Layer-2 devices are listed first; use Show all SNMP devices to reveal the rest.

Tune the interval if you need to

The default is 300 seconds for everything. Set a global default at the top of the card, or override it per device in the Interval column. Select several rows to apply a change in bulk.

Using a different credential for UDT

Each device can poll UDT with a credential different from its normal SNMP settings — useful when the bridge tables sit behind a v3 user with per-VLAN context rights while general monitoring uses a plain community. Pick it in the UDT credential column; Device SNMP settings means “inherit whatever the device already uses”.

08 Windows and Active Directory permissions #

User correlation is optional and entirely agentless. ZenPlus opens a WinRM session to each domain controller on a schedule, runs a read-only PowerShell query against the Security event log, and closes the session. Nothing is installed, nothing is written, and no other log is touched.

Which events are read

Event IDMeaningWhy UDT wants it
4624An account was successfully logged onCovers NTLM and non-Kerberos environments
4768A Kerberos authentication ticket (TGT) was requestedWorkstation IP at domain sign-in
4769A Kerberos service ticket was requestedOngoing user-to-IP association

Machine accounts (names ending in $) and the ANONYMOUS LOGON, SYSTEM, LOCAL SERVICE and NETWORK SERVICE principals are discarded before anything is stored, so the feed contains real users only.

The service account

Create one ordinary domain user — no administrative rights — and grant it exactly two things on the domain controllers. On a DC these are built-in domain-local groups in Active Directory, so add members with Add-ADGroupMember, not the local-group cmdlets:

# Run once, on any domain controller, as a Domain Admin

# 1. Read access to the Security event log
Add-ADGroupMember -Identity 'Event Log Readers'       -Members 'svc-zenplus-udt'

# 2. Permission to connect over WinRM without being an administrator
Add-ADGroupMember -Identity 'Remote Management Users' -Members 'svc-zenplus-udt'

Then make sure WinRM is listening on each DC. On most domain controllers it already is:

Get-Service WinRM                      # should be Running
winrm enumerate winrm/config/listener  # should show a listener on 5985 or 5986

# If not enabled yet:
Enable-PSRemoting -Force

Audit policy

The events must actually be logged. Kerberos auditing is on by default in the Default Domain Controllers Policy; logon auditing sometimes is not. Check and, if needed, enable success auditing for these three subcategories:

auditpol /get /subcategory:"Logon","Kerberos Authentication Service","Kerberos Service Ticket Operations"

auditpol /set /subcategory:"Logon" /success:enable
auditpol /set /subcategory:"Kerberos Authentication Service" /success:enable
auditpol /set /subcategory:"Kerberos Service Ticket Operations" /success:enable
Keep the Security log big enough

UDT reads at most 500 events per poll and resumes from the newest event it has already seen. On a busy domain controller a small, fast-rolling Security log combined with a long poll interval will lose logons between polls. Either shorten the interval or raise the log size.

curl -sk -o /dev/null -w '%{http_code}\n' http://dc01.corp.local:5985/wsman
# 405  → WinRM is listening (good)
# 000  → blocked or not listening

09 Adding a domain controller #

Store the Windows credential

Administration → Credentials → Windows. Enter the service account with its domain, and choose the authentication method — NTLM is the default and works in almost every environment. The password is encrypted at rest.

Add the controller

User Devices → Settings → Active Directory controllers → Add DC. Give it a name, the hostname or IP, the credential, and a poll interval (300 seconds by default, minimum 60).

Poll it once, immediately

Use the poll action on the row rather than waiting. The first poll looks back 30 minutes; after that each poll resumes from the newest event already recorded.

Read the status

The row shows last poll, status and the last error. Add every DC that authenticates users — a user is only seen by the controller that served their logon.

What happens next, and how logons are matched back to endpoints, is covered in User-to-device correlation.

10 Optional: remote port control #

The Switch Ports tab can shut down or re-enable a port directly. This is the one UDT feature that needs SNMP write access, because it performs an SNMP SET on ifAdminStatus (1.3.6.1.2.1.2.2.1.7).

  • With v2c, the device needs a read-write community.
  • With v3, the user's group needs a write view that includes 1.3.6.1.2.1.2.2.1.7.
  • Every attempt is written to the ZenPlus audit log with the operator, the outcome and any SNMP error, and appears in the UDT activity feed as a port action.
  • The action requires the operator role or higher.
Leave it off unless you want it

If you never grant write access, the rest of UDT is unaffected — the shutdown action simply fails with an SNMP error and is logged as such. Most deployments run UDT entirely read-only.
