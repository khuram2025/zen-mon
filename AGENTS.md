# Project guidance

## Credentials

- Keep private credentials in the workspace-root `.env.local`; load them without printing values. Never commit credentials, runtime state, private keys or generated packages.
- Document variable names with safe placeholders in `.env.example`. Ask for missing variables by name only.
- Never publish unsigned Windows installers or unsigned OTA packages.

## Source and releases

- The installed application lives under `/opt/zenplus`. Build and test in a separate checkout. Preserve appliance-local edits, compare fingerprints before deployment, and back up affected source and binaries.
- Continue source work through branches and pull requests. The sole repository owner explicitly authorized zero required independent approvals; retain all five required CI checks, conversation resolution and force-push/deletion protections. Do not reintroduce a second-reviewer requirement for this solo workflow. Follow the release runbooks with this owner-approved policy. Never bypass signing verification.
- Signed appliance-only releases are supported and preserve separately installed Windows agent packages. Windows installer signing is required when an installer is bundled, not for an appliance-only OTA package.
- Releases after 1.24.37 require the signed 1.24.36 Windows installer catalog bridge. Keep `scripts/release-policy.json` at 1.24.36 or higher; never lower it merely to permit a direct upgrade. Validate a genuine 1.24.29 -> 1.24.36 -> target canary path before promoting a dependent release, and retain published eligible bridge artifacts.
- Upgrade chain (see `docs/ota-upgrade-path-runbook.md`): releases stay cumulative and appliances pass only through required checkpoints, listed with a reason in `scripts/release-policy.json` (`required_checkpoints`; `minimum_supported_upgrade_base` is always the newest). The builder signs the newest checkpoint below a release as its minimum. The portal pauses a rollout by itself when more than its `max_failure_pct` of appliances fail the release (`integrations/zentryc_ota/upgrade_path.py`); a paused rollout resumes only through a new, reviewed rollout. Never raise the limit to push a failing release through.
- Release tarballs must normalize public code/assets to 0644 (executables/directories 0755), including nested dashboard archives. Verify permissions and service-account readability even when the build checkout uses umask 077. Never broaden appliance credential permissions. Rollback must stop binary consumers before legacy restore and replace running executable inodes atomically.
- Migration files and historical lockfile entries are append-only. Add a forward migration for new schema; ship the complete migration set.
- Run the strict dashboard build, route smoke checks, Python contracts and Go tests for the modules changed. Database integration tests require disposable fixtures, never installed application databases.
- `dashboard/src/main.tsx` and `App.tsx` define the active UI. Avoid reintroducing superseded duplicate pages or a second auth store.
- Dashboard look (see `docs/design-system.md`): use the rem type scale (`text-2xs` … `text-4xl`), never pixel font sizes, so the display density (compact/comfortable/large/NOC wall) scales every page; chart text goes through `chartFont()` and colours through `lib/chartTheme.ts`; KPI tiles use `components/ui/kpiTone.ts`. Everything the UI loads ships with the appliance (fonts via `@fontsource-variable`, no CDN); `scripts/test-offline-assets.mjs` enforces it.
- Every sidebar entry in `navigation.ts` declares the permission its page's API needs; `navAccess.ts` drives the sidebar, the route guard and the role editor preview, and `scripts/test-nav-access.mjs` enforces coverage. Servers use `servers.*`, APM uses `apm.*`. A user's visibility scope is their own `scope_tags` plus their role's `roles.scope_tags` (see `docs/role-based-navigation-and-team-scopes.md`). A role may be limited to selected pages and network maps (`roles.page_access`): the page list narrows the role's permissions server-side, so after changing `navigation.ts` regenerate `server/app/core/page_catalog.json` with `node scripts/test-page-access.mjs --write`.
- Service list headlines, daily bars and detail SLA explicitly use `basis=confirmed`: only confirmed incidents affect availability; isolated failed probes remain diagnostic evidence. Keep monitoring gaps unknown and retain configured retry thresholds. Batch list reports share `service_availability` segment conversion with detail and use the browser timezone for calendar days; legacy API defaults remain compatible.
- Device status is a confirmed state (see `docs/device-status-policy.md`): Degraded needs `degraded_confirm_checks` of the last `degraded_window_checks` checks, recovery uses separate recovery limits or a clean window, Down keeps `down_confirm_checks`, and flapping is a flag per change class (reachability, latency/loss), never a status value. The Go `poller/internal/devicestatus` and Python `app.services.device_status_machine` implementations must both pass `scripts/dev/device-status-contract/vectors.json`; change both and regenerate the vectors together. Only the polling owner runs the machine; `device_status_log` keeps confirmed transitions only. While flapping, status alerts are held (not dropped) for `flap_stable_minutes`.
- Metric alerts (host and SNMP) keep one incident per rule + asset + dimension with a breach hold (`min_duration`), a clear level (explicit reset or the 2-point auto clear for percent rules) and a stable-recovery hold (`clear_duration`, NULL = 300 s); missing samples never resolve. Never change customer thresholds to reduce noise. Every evaluator pass and the escalation sweeper take a cross-worker lock (`alert_worker_lock`), and every send for a known incident claims an `alert_delivery_keys` row (incident, event, channel, recipient) before it goes out (see `docs/alert-notification-policy.md`). Report schedules carry their own IANA `timezone`.
- Report delivery (see `docs/reports-delivery.md`): a run is written `running` first and finished with the email as sent and the attachment; temporary failures (connection, SMTP 4xx) retry from the stored email, permanent ones (5xx, missing channel) do not; share links expire and runs/artifacts follow `system_settings['reports']` retention; a failed section makes the run `partial`. The five legacy report types are retired: existing schedules run and convert, new ones are refused. Schedules store only existing, enabled channel ids and known scope keys.
- Alert storms (`docs/alert-storm-policy.md`, `app.services.alert_storm`, off by default): more than N distinct assets with the same event family in a scope within the window replace their per-asset sends (triggers, held members' recoveries, optionally escalations) with one combined notification per channel and recipient via `notification_digests` (reason `storm`); the storm gate runs before grouping in `dispatch_to_channels`. NCM comparison masks FortiOS per-print ciphertext (`docs/ncm-change-detection.md`); bump `NORMALIZATION_VERSION` when normalization changes.
- Shared alert rules are turned off for one device or server with an `alert_rule_exclusions` row, never by flipping `alert_rules.enabled` from an asset page (see `docs/alert-rule-exclusions.md`). Every evaluator that matches rules to devices or servers loads `alert_rule_exclusions.load()` once per pass and skips excluded pairs; excluding resolves that rule's open incidents on the asset without a recovery notice. Changing exclusions needs `alerts.manage` and the asset in the caller's scope.
- Escalation: incidents carry P1–P4 (`app.services.alert_priority`; NULL rule priority derives critical→P2, warning→P3, info→P4). Routing is rule policy > the rule's own legacy `escalation_levels` > priority default policy (a default never takes over a rule that already escalates). Acknowledgement stops steps but not review updates, and email links never mutate on GET. Every notification goes through `host_alert_service.dispatch_to_channels` with `alert_id` and `delivery_event`. Only P3/P4 warning/info triggers may be grouped into digests (`notification_grouping`, off by default).
- Device list/detail availability headlines share `/devices/dashboard/uptime-stats` and two-decimal formatting. Use `uptime_pct` and `sample_count` for partial failures; legacy rollup `is_up` is only a majority flag.
- The device page (`dashboard/src/pages/DeviceDetailPage.tsx` shell + `pages/device/`) keeps the confirmed status separate from the health rollup of `GET /devices/{id}/summary`; template shaping lives in `app.services.device_insights` (applicability via `applies_when`, offline rows blank their gauges). See `docs/device-detail-page.md`.
- Controller-managed children (see `docs/controller-managed-children.md`): FortiLink switches and FortiAPs are read through the FortiGate's own template rows (`managed_source`/`managed_instance`, raw index in `device_template_values.instance_oid`); never poll, ping or license them. Readings name the controller and measurement time, are marked stale after three polls (≥10 min), blank while the controller reports the child offline, and availability comes from controller-reported state with ≥90 % coverage or "insufficient history". `display: "children"` groups never appear on the controller's page; client identity needs `udt.view` (`udt.view_users` for user names). What the FortiGate MIB lacks is listed as unavailable, never guessed.
- Device Templates (see `docs/device-templates.md`): `device_profiles.oid_groups` is always the effective published document; change templates only through `app.services.device_templates` (draft → publish/pilot → revision + `device_profile_versions`), never by editing a built-in (customise creates an overlay child that keeps receiving release updates). The Go and Python classifiers must both pass `scripts/dev/template-match-contract/vectors.json`; change both and the vectors together. The classifier never overrides a set template (it records `profile_suggested_id` instead) and never assigns controller-managed children. `devices.device_type` references `device_types`; validate types against the catalogue. Template writes need `devices.manage_templates` and an unscoped user.
- Device groups and custom fields (see `docs/device-groups.md`): `device_group_members` is the one membership (sources `primary` = `devices.group_id`, kept by trigger; `static`; `rule` = dynamic groups, written only by `app.services.device_groups.membership.reconcile`). "Is this asset in group X" means `device_group_member_closure` (subgroups roll up) or `membership.groups_of`/`load` + `in_group`, never a bare `devices.group_id` comparison; this holds for every evaluator, maintenance (Python and the Go poller) and `alert_rule_scope`. A device's primary group must be static (`service.assert_static`). Dynamic conditions use the discovery-rules condition engine with the groups catalog (`facts.catalog`, `custom.<key>` facts); a failed evaluation keeps the previous members. Groups nest at most 5 levels and a group in use is not deleted. Custom fields are typed and separate from tags; keys and types never change. Group and field writes need `devices.manage_policies` and an unscoped user; values need `devices.manage`/`servers.manage` and the asset in scope.
- Thresholds per class (see `docs/alert-rule-overrides.md`): templates recommend rules (`rule_packs`: from metric warn/crit thresholds plus the template's `rule_pack`); nothing is created or enabled until an operator accepts one, which creates a normal rule with `profile_id` (template and those customised from it), `pack_key` and `pack_accepted`. A template revision never changes an accepted rule: a differing recommendation is shown with Apply/Keep. Per-asset changes to threshold, clear level, holds or priority are `alert_rule_overrides` rows (device/server rows before group rows, then position; first unexpired match wins, never merged); `network_alert_service` and `host_alert_service` load them once per pass with `alert_rule_overrides.load()`; turning a rule off stays an exclusion. Interface roles come from the template's ordered `interface_roles` or an operator's `device_interfaces.role`, select interfaces for `alert_rules.if_role`, and never change `monitored`. The device page colours template metrics with the effective rule level (`effective_thresholds`).
- Device widget layouts are scoped by user/device/tab and saved on the server (`device_widget_layouts`, browser storage is a cache). Vendor/type templates match normalized vendor + device type + tab + user; device overrides win. Preserve layout preferences for temporarily absent widgets.
- Storage: the data volume is whatever LV backs `/data` (often the root LV); never hardcode LV names. Disk/LVM changes go only through the root `scripts/zenplus-volume-helper`, which re-validates every request; tests fake its commands and never touch real disks. Pressure purging belongs to the independent watchdog (`storage_watchdog`/`storage_policy`, no PostgreSQL dependency); ClickHouse system logs stay bounded by `docker/clickhouse/zenplus_logging.xml`; host telemetry inserts go through `host_insert_batcher` (see `docs/storage-management.md`).
- System status (Settings, the tab that was Storage; see `docs/system-status.md`): the tab keeps the address `?tab=storage` (role page lists and links in sent reports refer to it); never rename the key. The appliance's own health comes from `app.services.appliance_health` (`/proc`, one unprivileged `systemctl show`, the data stores asked directly); a reading that cannot be taken is `null` and shown as unavailable, never zero. History is one sample a minute for 24 h in Redis, written by the worker that claims the minute; do not grow it into a telemetry pipeline. Units are found by pattern (`postgresql@*.service`), never by version. Storage sections keep product wording (no component, volume, table or path names); the overview names components beside what they do. A manual purge drops a partition only when its newest data can be dated; one backup or restore runs at a time.
- F5 overall RAM uses sysGlobalHostMemUsed / sysGlobalHostMemTotal, never the highest TMM/non-TMM percentage. Keep TMM, non-TMM and swap separate; use `f5_system_memory_pct` for corrected history. Missing sensors are not zero, and certificate inventory does not prove active TLS bindings.

- Network maps (see `docs/network-maps.md`): a node is exactly one device, server or service check. Discovered CDP/LLDP links are used only as current evidence (seen within 24 h, both ports present and up); stale rows are shown for review, never drawn silently, and interface names are stored in the device's own `if_name` spelling. Annotation cables change only through the row-locked annotation-link endpoints; deleting a node or shape prunes them. Site nodes (`widget: "site"` shapes) aggregate members through `GET /maps/{id}/sites-live`, which honours the viewer's visibility scope and page-access maps; the NOC wall (`?wall=1`) must work without the browser full-screen API, and `GET /maps` never returns background image bytes (see `Documentation/29-NETWORK-MAPS.md`).

- License capacity: a node is one device or one server; a server linked to its device counts once, controller children and service checks never count. `license_capacity.NODE_COUNT_SQL` and `updater/inventory.py` `NODE_COUNT_SQL` stay identical (the reported count is the enforced count). Every path that creates a device or server checks the capacity under the `license-node-capacity` advisory lock and refuses with 402 `license_capacity_reached`; enforcement never disables or deletes existing nodes (see `docs/license-capacity.md`).

- Discovery rules (see `docs/discovery-rule-engine.md`, `app.services.discovery_rules`, off by default via `system_settings['discovery_rules']`): global rules in priority order; the first matching rule wins each single value, tags merge. Preview, re-evaluation and the end-of-scan evaluation share `engine.evaluate` / `engine.disposition` / `runner.assign_capacity`, so a preview is what a run applies; keep it that way and extend `scripts/dev/discovery-rules-contract/vectors.json` when semantics change. The profile `import_mode` decides what rules may do (`review` annotates only). Auto-import goes through `app.services.discovery_import` (the Import dialog's path) under the `discovery-import` lock and the license budget, capped per scan with a license reserve. On existing devices/servers (`discovery_rules.inventory`) every rule-set value is an assignment with the value it replaced: set-once rules keep later hand edits, enforce rules put their value back, tags are only added, a credential never replaces a device's own SNMP settings, nothing is deleted or turned off (the one exception: an explicit interface *ignore* pattern sets `device_interfaces.monitored` false, owned and undoable like any value). Manual runs apply exactly the previewed changes (digest, 409 `preview_stale`); undo restores only values still equal to what the rule set and never deletes devices; the "when added" sweep (`zenplus:discovery_rules_pass`) evaluates each new asset once and only marks assets while the engine is off. Writes need `discovery.manage_rules`, activation and runs also the permissions of the values written, and tag-scoped users cannot change or run rules. Rules with the `changed` trigger re-evaluate only assets whose SQL facts fingerprint (status excluded) or rules revision changed (`discovery_rules.reconcile`, same pass/lock); a pass above `max_changes_per_run` applies nothing and waits for approve/reject; revert on un-match restores only values still equal to what the rule set. Controller-managed children are kind `child` with organising actions only. NCCM / Device Tracker / maintenance / alert exclusions per class belong to monitoring policies (Device Templates plan phase 4), not rule actions. Phase 4: automatic runs (`changed`, `scheduled`) also wait for approval above a rule's own `max_changes_per_run` or the match-growth stop (`growth_breaker_pct`/`_min` against `last_match_count`); topology facts use only current LLDP/CDP evidence via `map_topology.build_adjacencies`; "monitor from sensor" adds a `sensor_assignments` row only for an online, authorised sensor and never removes one; created service checks are never deleted by undo or un-match; facts needing extra queries load, and enter the fingerprint, only while a rule uses them (`inventory.needs`).

- SSH host keys (see `docs/ssh-host-key-trust.md`): the SSH terminal confirms unknown keys by fingerprint before sending a password and refuses changed keys; NCCM backups record the first key and only warn on change; UDT gateway collection enforces operator-registered keys only. Session tokens must carry a server-side session id (`jti`), never travel in a URL (streams use `?ticket=`), and the API refuses to start on placeholder secrets (`app.core.secret_policy`). Client addresses come from `app.core.client_ip`, never a client-supplied X-Forwarded-For hop.

- Directory accounts (LDAP / RADIUS / OIDC; see `docs/directory-account-roles.md`, `app.services.role_source`): the directory decides whether the account may sign in (it must authenticate and match a role mapping or the default role); the mapping decides its role unless an administrator set one by hand (`users.role_manual`), which sign-in then keeps. What the mapping gives is always recorded (`users.directory_role`), never dropped, and handing the role back applies it. Sign-in resolves usernames ignoring case (`auth._find_user`); never look a user up by exact-case username. The Settings SMTP tab reads and writes the default `notification_gateways` row (what senders use) and never returns the password.

## Device Tracker

- Sidebar groups and breadcrumb ownership are in `dashboard/src/components/layout/navigation.ts`. Device Tracker is separate from Monitoring.
- Preserve prior IP observation periods. Summarize repeated addresses for display; do not delete history to remove duplicates.
- ARP/ND sightings from separate reporters do not establish globally exclusive IP ownership. Interface indexes are reporter-local, not global subnet/VRF identifiers.
- `udt_ip_evidence` retains endpoint/IP/reporter/interface/source observations. Replacement primary addresses require three observations within 24 hours from one reporter/interface/source. Never fabricate repeat evidence from legacy history counts.

- Service confirmation uses 3 total attempts with a 10s completion-to-retry gap by default; healthy checks wait 60s and confirmed Down checks wait 30s. Preserve existing configured thresholds. Controller and capable sensors retain each attempt as diagnostics, publish progress without opening an incident, and recover on the first success. Legacy sensors submit final verdicts only. Migration 121 adds recovery interval and verification progress.
- Server availability (`server_availability.py`): an enabled `ping_status` rule that fires on down (`trigger_on = down`, or an `any` rule whose only condition is `ping_status == 0`, as seeded) with no device, group, type or location scope ("Device Down") also pages agent servers whose heartbeat is silent and that ping cannot vouch for; `scope_tag` narrows servers like devices. A silent agent on a server whose linked ping device is up is `host_agent_offline` (seeded P3 rule), never Down; a linked device that is down is left to the device path, one in maintenance pages nobody. The silence allowance is the rule's `min_duration`, else 180 s (floor 90 s). A server already silent before `alerts.server_availability_since` (system_settings, recorded on the first evaluation) is recorded with notified=false and never paged, so an upgrade does not page old outages. An availability incident resolves the sweep's built-in `agent_offline` alert, which has no rule or route and is raised only for a server no availability rule covers.
