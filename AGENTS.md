# Project guidance

## Credentials

- Keep private credentials in the workspace-root `.env.local`; load them without printing values. Never commit credentials, runtime state, private keys or generated packages.
- Document variable names with safe placeholders in `.env.example`. Ask for missing variables by name only.
- Never publish unsigned Windows installers or unsigned OTA packages.

## Source and releases

- The installed application lives under `/opt/zenplus`. Build and test in a separate checkout. Preserve appliance-local edits, compare fingerprints before deployment, and back up affected source and binaries.
- Continue source work through branches and pull requests. The sole repository owner explicitly authorized zero required independent approvals; retain all five required CI checks, conversation resolution and force-push/deletion protections. Do not reintroduce a second-reviewer requirement for this solo workflow. Follow the release runbooks with this owner-approved policy. Never bypass signing verification.
- Signed appliance-only releases are supported and preserve separately installed Windows agent packages. Windows installer signing is required when an installer is bundled, not for an appliance-only OTA package.
- Release tarballs must normalize public code/assets to 0644 (executables/directories 0755), including nested dashboard archives. Verify permissions and service-account readability even when the build checkout uses umask 077. Never broaden appliance credential permissions. Rollback must stop binary consumers before legacy restore and replace running executable inodes atomically.
- Migration files and historical lockfile entries are append-only. Add a forward migration for new schema; ship the complete migration set.
- Run the strict dashboard build, route smoke checks, Python contracts and Go tests for the modules changed. Database integration tests require disposable fixtures, never installed application databases.
- `dashboard/src/main.tsx` and `App.tsx` define the active UI. Avoid reintroducing superseded duplicate pages or a second auth store.
- Every sidebar entry in `navigation.ts` declares the permission its page's API needs; `navAccess.ts` drives the sidebar, the route guard and the role editor preview, and `scripts/test-nav-access.mjs` enforces coverage. Servers use `servers.*`, APM uses `apm.*`. A user's visibility scope is their own `scope_tags` plus their role's `roles.scope_tags` (see `docs/role-based-navigation-and-team-scopes.md`).
- Service list headlines, daily bars and detail SLA explicitly use `basis=confirmed`: only confirmed incidents affect availability; isolated failed probes remain diagnostic evidence. Keep monitoring gaps unknown and retain configured retry thresholds. Batch list reports share `service_availability` segment conversion with detail and use the browser timezone for calendar days; legacy API defaults remain compatible.
- Device status is a confirmed state (see `docs/device-status-policy.md`): Degraded needs `degraded_confirm_checks` of the last `degraded_window_checks` checks, recovery uses separate recovery limits or a clean window, Down keeps `down_confirm_checks`, and flapping is a flag per change class (reachability, latency/loss), never a status value. The Go `poller/internal/devicestatus` and Python `app.services.device_status_machine` implementations must both pass `scripts/dev/device-status-contract/vectors.json`; change both and regenerate the vectors together. Only the polling owner runs the machine; `device_status_log` keeps confirmed transitions only. While flapping, status alerts are held (not dropped) for `flap_stable_minutes`.
- Metric alerts (host and SNMP) keep one incident per rule + asset + dimension with a breach hold (`min_duration`), a clear level (explicit reset or the 2-point auto clear for percent rules) and a stable-recovery hold (`clear_duration`, NULL = 300 s); missing samples never resolve. Never change customer thresholds to reduce noise. Every evaluator pass and the escalation sweeper take a cross-worker lock (`alert_worker_lock`), and every send for a known incident claims an `alert_delivery_keys` row (incident, event, channel, recipient) before it goes out (see `docs/alert-notification-policy.md`). Report schedules carry their own IANA `timezone`.
- Report delivery (see `docs/reports-delivery.md`): a run is written `running` first and finished with the email as sent and the attachment; temporary failures (connection, SMTP 4xx) retry from the stored email, permanent ones (5xx, missing channel) do not; share links expire and runs/artifacts follow `system_settings['reports']` retention; a failed section makes the run `partial`. The five legacy report types are retired: existing schedules run and convert, new ones are refused. Schedules store only existing, enabled channel ids and known scope keys.
- Escalation: incidents carry P1–P4 (`app.services.alert_priority`; NULL rule priority derives critical→P2, warning→P3, info→P4). Routing is rule policy > the rule's own legacy `escalation_levels` > priority default policy (a default never takes over a rule that already escalates). Acknowledgement stops steps but not review updates, and email links never mutate on GET. Every notification goes through `host_alert_service.dispatch_to_channels` with `alert_id` and `delivery_event`. Only P3/P4 warning/info triggers may be grouped into digests (`notification_grouping`, off by default).
- Device list/detail availability headlines share `/devices/dashboard/uptime-stats` and two-decimal formatting. Use `uptime_pct` and `sample_count` for partial failures; legacy rollup `is_up` is only a majority flag.
- The device page (`dashboard/src/pages/DeviceDetailPage.tsx` shell + `pages/device/`) keeps the confirmed status separate from the health rollup of `GET /devices/{id}/summary`; template shaping lives in `app.services.device_insights` (applicability via `applies_when`, offline rows blank their gauges). See `docs/device-detail-page.md`.
- Device widget layouts are scoped by user/device/tab and saved on the server (`device_widget_layouts`, browser storage is a cache). Vendor/type templates match normalized vendor + device type + tab + user; device overrides win. Preserve layout preferences for temporarily absent widgets.
- Storage: the data volume is whatever LV backs `/data` (often the root LV); never hardcode LV names. Disk/LVM changes go only through the root `scripts/zenplus-volume-helper`, which re-validates every request; tests fake its commands and never touch real disks. Pressure purging belongs to the independent watchdog (`storage_watchdog`/`storage_policy`, no PostgreSQL dependency); ClickHouse system logs stay bounded by `docker/clickhouse/zenplus_logging.xml`; host telemetry inserts go through `host_insert_batcher` (see `docs/storage-management.md`).
- F5 overall RAM uses sysGlobalHostMemUsed / sysGlobalHostMemTotal, never the highest TMM/non-TMM percentage. Keep TMM, non-TMM and swap separate; use `f5_system_memory_pct` for corrected history. Missing sensors are not zero, and certificate inventory does not prove active TLS bindings.

- Network maps (see `docs/network-maps.md`): a node is exactly one device, server or service check. Discovered CDP/LLDP links are used only as current evidence (seen within 24 h, both ports present and up); stale rows are shown for review, never drawn silently, and interface names are stored in the device's own `if_name` spelling. Annotation cables change only through the row-locked annotation-link endpoints; deleting a node or shape prunes them.

- License capacity: a node is one device or one server; a server linked to its device counts once, controller children and service checks never count. `license_capacity.NODE_COUNT_SQL` and `updater/inventory.py` `NODE_COUNT_SQL` stay identical (the reported count is the enforced count). Every path that creates a device or server checks the capacity under the `license-node-capacity` advisory lock and refuses with 402 `license_capacity_reached`; enforcement never disables or deletes existing nodes (see `docs/license-capacity.md`).

- SSH host keys (see `docs/ssh-host-key-trust.md`): the SSH terminal confirms unknown keys by fingerprint before sending a password and refuses changed keys; NCCM backups record the first key and only warn on change; UDT gateway collection enforces operator-registered keys only. Session tokens must carry a server-side session id (`jti`), never travel in a URL (streams use `?ticket=`), and the API refuses to start on placeholder secrets (`app.core.secret_policy`). Client addresses come from `app.core.client_ip`, never a client-supplied X-Forwarded-For hop.

## Device Tracker

- Sidebar groups and breadcrumb ownership are in `dashboard/src/components/layout/navigation.ts`. Device Tracker is separate from Monitoring.
- Preserve prior IP observation periods. Summarize repeated addresses for display; do not delete history to remove duplicates.
- ARP/ND sightings from separate reporters do not establish globally exclusive IP ownership. Interface indexes are reporter-local, not global subnet/VRF identifiers.
- `udt_ip_evidence` retains endpoint/IP/reporter/interface/source observations. Replacement primary addresses require three observations within 24 hours from one reporter/interface/source. Never fabricate repeat evidence from legacy history counts.

- Service confirmation uses 3 total attempts with a 10s completion-to-retry gap by default; healthy checks wait 60s and confirmed Down checks wait 30s. Preserve existing configured thresholds. Controller and capable sensors retain each attempt as diagnostics, publish progress without opening an incident, and recover on the first success. Legacy sensors submit final verdicts only. Migration 121 adds recovery interval and verification progress.
